# Componentes PO-UI — Fase 2 (estrutura, dados, entradas, processos e retorno) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Completar o conjunto v1 de componentes PO-UI da spec (menu lateral, várias páginas, contêineres, abas, árvore, lista, info, progresso, gauge, gráfico, campos tipados), processos filhos com saída ao vivo (`PoApp:Spawn`) e retorno ao usuário (`Notify`, `Confirm`, `Loading`).

**Architecture:** Estende o modelo da fase 1 (`pkg/vm/poui*.go`): `poAppState` passa a ter várias páginas, uma página corrente e um menu. As operações não-patch (`notify`/`confirm`/`loading`) viajam no mesmo `batch`, na ordem. `Spawn` roda o processo sem shell numa goroutine que posta linhas com **contrapressão** (`UIPostWait`, método novo de `ComponentUI`), para não perder saída. O frontend ganha os novos tipos no `UiHostComponent` e o layout `po-wrapper` com `po-menu`.

**Tech Stack:** Go 1.27 (sem CGO), Angular 21 + `@po-ui/ng-components` 21.23 (instalado).

**Spec:** `docs/superpowers/specs/2026-11-20-poui-componentes-design.md` (fase 2 da seção 8, e `PoApp:Navigate`/`Spawn`/`Notify`/`Confirm` da seção 6.2). Base: fase 1, já no `master` (64d9d2d).

## Global Constraints

- AdvPP **100% compatível**: todo teste existente passa; programas da fase 1 se comportam igual.
- **Executáveis para macOS, Linux e Windows** em toda task: `go test ./...` verde e builds `linux/amd64`, `linux/arm64`, `windows/amd64` e `darwin/arm64` com `CGO_ENABLED=0`, gerados **fora** da raiz do repositório. `TestBytecodeDeterminism` verde.
- `Spawn` executa **sem shell** (`exec.Command(prog, args...)`). Nenhuma interpretação de `;`, `|`, `$`.
- Goroutines auxiliares (timers, processos) **só postam** eventos e nunca tocam a VM.
- Processos de `Spawn` são **encerrados** quando o laço termina (Close ou sessão abandonada).
- Nomes `Po*` novos cedem a funções do programa com o mesmo nome (mapa `poClassNames` do codegen).
- Somente modo web; frontend genérico. Build do frontend: `cd web && npx ng build` e cópia de `web/dist/advpp-web/browser/.` para `pkg/webui/dist/`.
- Textos, comentários e commits em português, sem linhas de atribuição.

## Review Focus

1. Navegador fecha com `Spawn` rodando: o processo filho é morto e não fica órfão. Teste em Task 3 (`TestSpawnMortoAoFecharSessao`).
2. Processo que imprime milhares de linhas: nenhuma linha se perde e o laço não trava. Teste em Task 3 (`TestSpawnNaoPerdeLinhas`, 5000 linhas).
3. Programa inexistente em `Spawn`: `bFim` recebe `-1`, sem pânico. Teste em Task 3 (`TestSpawnProgramaInexistente`).
4. `Navigate` para página de outra aplicação, ou `SetCols` fora de 1..12: erro claro. Teste em Task 1 (`TestNavigatePaginaAlheia`, `TestSetColsInvalido`).
5. Resposta de `Confirm` repetida ou com id desconhecido: ignorada (o bloco roda uma vez só). Teste em Task 3 (`TestConfirmRespostaUnica`).

## Protocolo — acréscimos (fixados para todas as tasks)

- `mount` ganha `"menu": <nó>|null`; `"tree"` é a **página corrente**. `Navigate` com a tela ativa reenvia `mount` ao fim do handler, e as ops não-patch do lote vão depois dele.
- Ops novas, dentro de `batch.ops`, na ordem em que o AdvPL as gerou:
  `{"op":"notify","text":"...","type":"success|warning|error|information"}`,
  `{"op":"confirm","id":N,"title":"...","text":"..."}` (resposta: `POST /ui {"id":N,"event":"confirm","value":true|false}`),
  `{"op":"loading","on":true,"text":"..."}`.
  Ops geradas antes do `Activate` são enviadas logo depois do `mount`.
- Eventos internos de processo: `id=<id do spawn>`, `event="line"`, `value={"t":"texto","e":false}` e `event="exit"`, `value=<código>`.

| type | props | eventos (value) → argumentos do bloco |
|---|---|---|
| `menu` | `items:[{label,icon,index}]` | `action` (índice) → `(oMenu)` |
| `container` | `title` | — |
| `widget` | `title` | — |
| `divider` | `label` | — |
| `tabs` | — | — |
| `tab` | `label`, `active` | — |
| `tree` | `items:[{label,value,subItems}]` | `select` (value texto) → `(o, cValor)` |
| `list` | `items:[{title,detail}]` | `select` (índice) → `(o, aLinha)` |
| `info` | `label`, `value` | — |
| `progress` | `value` (0–100), `text` | — |
| `gauge` | `title`, `value` (0–100), `description` | — |
| `chart` | `title`, `type`, `categories`, `series:[{label,data}]` | — |
| `password`/`textarea` | `label`, `value` | `change` → `(o, cTexto)` |
| `number` | `label`, `value` | `change` → `(o, nValor)` |
| `select` | `label`, `options:[{label,value}]`, `value` | `change` → `(o, cValor)` |
| `checkbox`/`switch` | `label`, `value` (bool) | `change` → `(o, lValor)` |

Prop comum nova: `cols` (1–12) → largura na grade PO (`po-md-<cols>`), ausente = 12.

### Task 3: Processos (`Spawn`), `Confirm` e `Loading`

**Files:**
- Create: `pkg/vm/poui_spawn.go`
- Modify: `pkg/vm/poui.go` (`ComponentUI` ganha `UIPostWait`; `poAppState` ganha `spawns`, `confirms`), `pkg/vm/poui_native.go`, `pkg/vm/poui_loop.go`
- Modify: `pkg/webui/ui.go` (`UIPostWait`)
- Test: `pkg/vm/poui_spawn_test.go`, `pkg/webui/ui_test.go`

**Interfaces:**
- Produces (Go):
  - `ComponentUI.UIPostWait(id int, event string, value []byte) bool`: bloqueia até enfileirar; com a sessão encerrada devolve `false` sem bloquear. O `Provider` implementa com um `select` em `s.ui`/`s.quit`.
  - `type poSpawn struct { cmd *exec.Cmd; prog string; args []string; bLinha, bFim advplrt.Value; iniciado bool }`
  - `func (a *poAppState) startSpawn(id int, sp *poSpawn)`: `exec.Command(prog, args...)`, stdout e stderr lidos linha a linha (`bufio.Scanner` com buffer de 1 MB) e postados com `UIPostWait`; depois de `Wait`, `exit` com o código. Falha ao iniciar → `exit` com `-1`.
- Produces (AdvPL):
  - `PoApp:Spawn(cProg, aArgs, bLinha, bFim) -> nId`. Antes do `Activate`, o processo começa no `Activate`, como os timers. `bLinha(cLinha, lErro)`, `bFim(nCodigo)`.
  - `PoApp:KillSpawn(nId)`: mata o processo (idempotente).
  - `PoApp:Confirm(cTexto, bSim[, bNao[, cTitulo]])`: id de `nextID`; resposta `confirm` com `true` → `bSim`, com `false` → `bNao`. O registro é apagado depois da primeira resposta.
  - `PoApp:Loading(lAtivo[, cTexto])` → op `loading`.
  - No fim do laço (Close ou Goexit), `defer` mata os processos vivos (`cmd.Process.Kill()`).

- [ ] **Step 1: Testes que falham** (Linux/macOS; no Windows, `t.Skip` nos que usam `sh`/`seq`)
